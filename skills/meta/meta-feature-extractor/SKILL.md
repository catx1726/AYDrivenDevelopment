# Meta Feature Extractor (Business & Feature → Reproduction Blueprint)

## Overview

把"一个完整业务功能"提炼为一份**双向可用的复现蓝图**：
- **AI** 读了能从零重建该功能
- **人类** 读了能懂业务用途、目的、实现与坑

与 `meta-distiller` 互补：distiller 收割**纯代码逻辑**为可复用代码资产；本技能提炼**整个功能/业务**为可复现文档。

## 三原则（不可妥协）

1. **双向可逆**：同一套 7 层结构既适用逆向（代码→文档），也适用正向（PRD→文档），仅每层的"证据来源"不同
2. **最小可复现单元 = L0 + L1 + L2 + L5**：缺受众路径/业务意图/术语表/数据契约任一，AI 无法可靠重建——这四层**强制必填**
3. **行级证据优先**：所有断言带 `文件:行号`；只有文件名没有行号视为**证据不足**，等同于捏造

## The Stance（双姿态）

- **考古学家**：只引证不臆断；每个结论追溯到 `file:line`；代码未明示处明确标注"未明示"
- **架构师**：不只描述"现在怎样"，永远追问"如何重建、可否简化"

## When to Use

- 把现有模块逆向为设计文档（brownfield）
- 把需求/PRD 正向转为可实施 spec（greenfield）
- 跨项目复用一个功能、需要交接给陌生 AI/人

## When NOT to Use

- 只复用一个函数/算法 → 用 `meta-distiller`
- 写用户手册/API 参考 → 直接写，不需要本技能
- 改 bug → 用 `systematic-debugging`

## Boundaries（与 meta-distiller 的分界）

| 维度 | meta-distiller | 本技能 |
|---|---|---|
| 对象 | 纯逻辑/Hooks/算法 | 整个功能（UI+流程+数据+业务） |
| 产出 | 可执行代码 pattern | 复现级设计文档 |
| 粒度 | 微观（函数） | 宏观（功能） |
| 落点 | `skills/` 代码资产 | `docs/` 设计蓝图 |

## 核心：7 层功能蓝图

每层 = 回答什么 + 框架 + 必产 + 强制等级。🔴 = 强制必填（RED 实测 naive AI 易漏）；🟡 = 推荐。

| 层 | 回答 | 框架 | 必产 | 等级 |
|---|---|---|---|---|
| **L0** | 给谁看/怎么读 | Diátaxis | 阅读路径表 + 一页速查表（"想做什么→看哪"） | 🔴 |
| **L1** | 为什么/谁用/啥痛 | **JTBD + 5W2H + 5 Whys** | 业务背景 + JTBD 句式 + 典型场景叙事 | 🔴 |
| **L2** | 领域术语 | **DDD 统一语言** | 名词表（中文/英文/代码标识三列） | 🔴 |
| **L3** | 怎么走完流程 | **Event Storming + 故事地图** | Mermaid 流程图 + 步骤 | 🟡 |
| **L4** | 技术怎么搭 | **C4 模型** | 技术栈 + 目录树 + 路由表 + 外部依赖 | 🟡 |
| **L5** | 实体/接口/状态 | **DDD 实体 + CRUD 矩阵 + ER 图** | 字段表 + API 表（方法/URL/入参/出参）+ 枚举 | 🔴 |
| **L6** | 非显然实现 | **时序图 + 决策表 + 状态机** | 至少 1 个关键机制时序图 | 🟡 |
| **L7** | 怎么重做/有啥坑 | **MoSCoW + 反模式清单** | MVP 优先级 + 技术债 + 重构建议 | 🟡 |

**层合并规则**：简单功能可合并 L3+L4、L6+L7；但 **L0/L1/L2/L5 不可省**。

### 每层的"最小强制项"（RED 实测教训）

> 这些是 naive AI 在盲测（项管日志提炼）中真实暴露的系统性缺陷，技能必须强制对冲。

- **L0 强制**：必须给"AI 怎么读 vs 人类怎么读"**两条阅读路径**；必须有**一页速查表**。naive AI 常口头声明"面向双受众"却不出路径，导致全文细节墙。
- **L1 强制**：必须填 **JTBD 句式模板**：`When [情境], 我想要 [动机], 以便 [预期成果]`（每角色一条）；必须答"**谁用**（角色）+ **解决什么痛**"。naive AI 常只写"它是什么"不写"它为什么存在"。
- **L2 强制**：术语表必须**三列**（中文/英文/代码标识），消除 `plrId/projectLogId/pltId/plmsId` 这类裸 id 歧义。
- **L5 强制**：**分离 UI 配置 vs 数据模型**——UI 渲染配置（表格列定义、表单项）不是数据模型，单列说明；API 表每条必须有 **方法/URL/入参/出参** 四列。naive AI 常把表格列定义混进字段表，且 API 缺方法列。
- **全局证据强制**：所有断言 `file:line`；证据不足时标"**代码未明示**"，**禁止编造**。

## 框架速查（每个：是什么/何时用/3 步/映射层/实例）

### JTBD（Jobs-to-be-Done）→ L1
- **是什么**：用户"雇佣"功能来完成的任务
- **3 步**：①列角色 ②对每角色填 `When__, I want__, so I can__` ③推导核心价值
- **实例**（监理日志 §1.2）：监理工程师——"当每天巡视结束，我想要按版块记录现场情况，以便竣工验收时能取证"

### 5W2H → L1
- Who（角色）/What（是什么）/When&Where（场景）/Why（为什么）/How（大致用法）/How much（频次/价值）
- 与 JTBD 互补：JTBD 抓动机，5W2H 抓全景

### 5 Whys → L1
- 连问"为什么"挖到根目的。把"它做 X"挖到"它解决 Y 问题"。逆向提炼时尤其有用（代码只告诉你"做什么"）。

### DDD 统一语言 → L2
- **是什么**：开发与领域专家共享、消除翻译损耗的术语表
- **3 步**：①扫代码标识 ②回溯业务原意 ③建中英对照表
- **实例**（监理日志 §1.3）：日志/ProjectLog/projectLogId；版块/Module/plmId；记录/ProjectLogRecord/plrId

### DDD 实体 + 聚合 + CRUD 矩阵 → L5
- 区分 **Entity**（有身份/id，如 ProjectLogRecord）/ **Value Object**（无 id，如 WeatherData）/ **Aggregate**（一致性边界）
- **CRUD 矩阵**：实体 × {Create/Read/Update/Delete} 交叉表，每个格子映射到 API。**防漏端点**——空格说明该操作依附别处或缺失
- **实例**：ProjectLogRecord × {C:依附于 saveContent / R:getRecordList / U:saveContent / D:无} → 暴露"创建依附保存"的契约特征

### Event Storming → L3
- **是什么**：用"领域事件"（过去式）+ 命令 + 角色梳理流程
- **3 步**：①列事件（日志已保存/锁已释放）②连命令（点保存/离开页面）③标角色
- **实例**（监理日志 §2.3）：抢锁→编辑→保存→放锁→轮询同步

### C4 模型 → L4
- Context（外部依赖）/Container（技术栈）/Component（目录与文件）/Code（类与字段）
- L4 通常做到 **Component 级**。**实例**（监理日志 §3）：技术栈表 + 目录树 + 路由表 + 外部依赖

### UML 时序图 / 状态机 / 决策表 → L6
- **时序图**：多角色交互（协同锁、轮询同步）— 监理日志 §6.2
- **状态机**：实体状态流转（plrState: 未完成↔已完成）
- **决策表**：多条件分支（天气三级回退：已存?→当天?→占位）— 监理日志 §6.7

### MoSCoW → L7
- **M**ust / **S**hould / **C**ould / **W**on't 优先级，给重建排序。**实例**（监理日志 §7.2 P0-P3）

### Diátaxis → L0
- 文档四模式：教程（学）/操作指南（做）/参考（查）/解释（懂）
- L0 据此切分：**AI 读参考+操作指南**（L2/L3/L4/L5/L6/L7），**人类读解释+教程**（L1/典型场景）

## 方向适配（逆向 vs 正向）

| 层 | 逆向（代码→文档）证据来源 | 正向（PRD→文档）证据来源 |
|---|---|---|
| L1 | 5 Whys 追问代码背后的业务；读 git log/commit message | PRD 的"业务背景/目标"段 |
| L2 | 扫代码标识回溯业务原意 | PRD 术语表 + 访谈领域专家 |
| L5 | 抽取真实字段/接口；**多一栏"现状技术债"** | 设计字段/接口；**多一栏"验收标准"** |
| L7 | 现状重构建议 | 实施优先级 + 风险 |

同一套 7 层两边通用，差异仅在每层的"证据来源"与 L5/L7 的一栏附加项。

## 实施工作流

1. **范围确认**：与 Driver 对齐"提炼哪个功能 + 逆向/正向 + 输出位置"。混入兄弟功能是范围失控（虽 RED 实测 naive AI 此项可控，仍需警惕）
2. **发现**：通读目录；列文件清单（行数）；定位 API 文件、路由、store、入口组件
3. **逐层填充**：按 L0→L7 顺序，每层用对应框架驱动；🔴 层不齐则**停**，不可跳过
4. **证据复核**：全文搜索每个断言是否有 `file:line`；无则补或标"代码未明示"
5. **自检**：跑下方"自检清单"
6. **Driver 审查**：交付前 Driver 至少审 **L1**（业务对不对）+ **L5**（契约对不对）

## 自检清单（RED 四缺陷专项 + 其余层）

### 🔴 L1 业务意图（RED 缺陷 #1）
- [ ] 有 JTBD 句式（每角色一条 `When/I want/so I can`）
- [ ] 答了"**谁用** + **解决什么痛**"（不止"是什么"）
- [ ] 有典型场景叙事（一个真实用户的一天）

### 🔴 L0 受众分层（RED 缺陷 #4）
- [ ] 有"AI 怎么读 vs 人类怎么读"**阅读路径表**
- [ ] 有一页**速查表**（"想做什么→看哪"）

### 🔴 行级证据（RED 缺陷 #8）
- [ ] 抽查 5 处断言，**全部带 `file:line`**
- [ ] 无证据处标注"代码未明示"，**未编造**

### 🔴 L5 数据契约纯度（RED 缺陷 #3）
- [ ] **UI 渲染配置（表格列/表单项）与数据模型分离**
- [ ] API 表每条有 **方法/URL/入参/出参** 四列
- [ ] 有 CRUD 矩阵或 ER 图

### 🟡 其余层
- [ ] L2 术语表三列齐全（中/英/代码标识）
- [ ] L3 有 Mermaid 流程图
- [ ] L4 有目录树 + 路由表
- [ ] L6 至少 1 个时序图或决策表
- [ ] L7 有 MoSCoW 优先级 + 技术债清单

## Anti-Patterns / Red Flags

| 反模式 | 实例（RED 实测） | 对策 |
|---|---|---|
| 业务意图只写"是什么" | "项管日志是结构化工程日报"——缺 WHY/WHO/PAIN | 强制 JTBD 句式 |
| 受众分层空转 | 开头写"面向 AI+人类"，全文无阅读路径 | 强制 L0 阅读路径表 + 速查表 |
| 文件级而非行级证据 | "见 write/index.vue"无行号 | 全局行级证据规则 |
| UI 配置混入数据模型 | 把表格列定义当字段表 | 强制 L5 分离 |
| 把兄弟功能混入主体 | 月报塞进核心日志文档 | 范围确认步骤；超范围功能仅 §1.4 一句话提及 |
| 凭空捏造字段 | 编造不存在的 API 参数 | "代码未明示"标注 |
| 全文细节墙无导航 | 顺序章节堆叠，难跳读 | L0 速查表 + 双阅读路径 |

**执行中自查（念头出现即 STOP）**：
- "功能定位我已经写了" → 检查是否答了 WHY 而非 WHAT
- "这个字段我猜是…" → 改为读代码或标"未明示"
- "读者自己会知道怎么看" → 不，必须给阅读路径
- "API 太多列不全" → 至少给方法/URL/入参/出参，不全则分域详列

## 参考实现

- **正例**：`D:\code\2026\Learn-Learn-Learn\项目模块文档\监理日志模块.md`（7 层完整 + 行级证据 + 双受众路径 + 速查表）——本技能的最佳参考样本
- **反例（RED 基线）**：naive AI（未经本技能训练）提炼项管日志 `src/views/project/projectmanage_log/` 的产出。其在 L1（业务意图浅）/L0（受众分层空转）/证据（文件级非行级）/L5（UI 配置混入数据模型）四项系统性失败，可作为对照理解本技能的强制力来源
