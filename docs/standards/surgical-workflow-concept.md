# 针对已有功能的“手术切入式”开发工作流 (Surgical Workflow Concept)

## 1. 背景与上下文 (Context)

在处理本项目已有功能（Bug 修复、逻辑微调、重构）时，现有的标准工作流（基于 `AGENTS.md` 的 Spec -> Issue -> Plan -> TDD 闭环）被识别出存在以下痛点：

*   **文档负担重 (A)：** 为几行代码的变更编写详尽的设计规范 (Spec) 和实施计划 (Plan) 投入产出比低。
*   **流程链条长 (B)：** 强隔离的流程（Issue/Branch/Spec）在处理紧急修复或微小改进时，反馈周期过慢。
*   **既有代码理解成本高 (C)：** 面对庞大且复杂的既有代码库，阅读和理解业务逻辑耗费了超过 70% 的精力。
*   **TDD 介入困难：** 在没有测试覆盖的旧代码中直接实施 TDD 往往无从下手。

**目标：** 制定一套“自底向上”的流程，利用 AI 的分析能力快速定位并理解逻辑，在保障质量的前提下跳过沉重的文档环节。

---

## 2. 工作流核心阶段

本工作流通过“理解-锁定-实施”的逻辑，确保对既有系统的修改既快速又安全。

### 阶段 1：逻辑 MRI (Logic MRI & Mapping)
**目标：** 在不通读全量代码的情况下，精准锁定逻辑位置与影响范围。
*   **动作：** AI 针对用户提供的模糊入口点（如函数名、关键字、类名）进行全量扫描。
*   **输出：** 
    *   **逻辑简报：** 用自然语言解释当前业务逻辑：“当 X 发生时，系统执行 Y，最后产生 Z。”
    *   **影响地图：** 标注关键调用链、状态变更点、副作用（数据库写入、外部 API 调用）。
*   **解决：** 阅读代码费时费力的问题。

### 阶段 2：建立安全垫 (Safety Net / Characterization Tests)
**目标：** 锁定现状，防止在修补 A 时意外破坏 B。
*   **动作：** AI 编写**特征测试 (Characterization Tests)**。
*   **核心逻辑：** 这种测试不关注“正确性”（可能代码本身就有 Bug），而是记录代码目前的实际输出。
*   **意义：** 为改动提供即时反馈。如果改动意外影响了未预料到的逻辑，特征测试会立即报警。
*   **解决：** 面对复杂代码不敢改、补测试成本高的问题。

### 阶段 3：Surgical Plan (极简计划)
**目标：** 跳过 Spec 文档，直接进入可执行步骤。
*   **动作：** 在 `writing-plans` 技能引导下，生成仅关注改动差异的实施计划。
*   **差异点：** 计划直接引用 MRI 阶段发现的逻辑点，减少背景描述，专注于代码层面的 Action。
*   **解决：** 文档冗余与流程摩擦。

### 阶段 4：TDD 增量开发
**目标：** 保证新逻辑的正确性。
*   **动作：** 遵循标准 TDD（红-绿-重构）编写新功能的测试并实施代码。
*   **验证：** 此时运行测试套件应包含：**特征测试（防退化）+ 新 TDD 测试（验正确）**。

### 阶段 5：验证与提纯 (Verify & Distill)
**目标：** 完成闭环。
*   **动作：** 通过 `verification-before-completion` 产出证据。
*   **提纯：** 观察此改动是否包含可提取到“母库”或“资产库”的通用模式。

---

## 3. 使用建议

*   **适用场景：** Bug 修复、既有业务逻辑调整、非结构性重构。
*   **不适用场景：** 全新功能开发、涉及重大架构变更的任务（仍应遵循标准 Spec 流程）。
*   **执行备注：** 执行过程中应继续使用 `worktree` 保持工作区隔离。
