# 棘手问题归档指南 (Debugging Recipes)

## 目的

记录那些“表象简单、根因隐蔽”的问题，帮助团队共同成长，避免重复踩坑。每次解决完一个棘手问题后，应将其归档到项目 `docs/playbooks/` 目录下。

## 什么算“棘手”

满足以下任一条件即可归档：

- 花 ≥2 轮才定位或修复
- 涉及跨组件、跨 context、跨进程的隐式行为
- 根因和表象不一致（例如报错位置不是真正出错位置）
- 调试过程中使用了值得复用的技巧或工具
- 未来很可能以不同形式再次出现
- 修复方案包含非显而易见的权衡或规避手段

---

## 归档格式

每个案例使用以下结构：

```markdown
# <简短标题>

## 现象 (Symptom)

用户/测试观察到的异常行为。

## 根因 (Root Cause)

逐层剖析后的真正原因。必须解释“为什么”会这样，而不仅是“是什么”。

## 调试路径 (Debugging Trail)

1. 第一步怀疑什么？验证结果如何？
2. 第二步又发现了什么矛盾？
3. 最终如何锁定根因？

## 修复方案 (Fix)

- 改了什么文件
- 关键代码片段
- 为什么这样改能解决问题

## 经验教训 (Lessons)

- 以后遇到类似现象应优先检查什么
- 应避免的假设
- 可复用的调试技巧

## 关联代码

- `src/...`
- `src/...`

## 关联 Issue/PR

- Issue #N
- PR #M
```

---

## 归档流程

1. **解决问题后**，AI 引擎判断是否符合“棘手”标准。
2. **在 `docs/playbooks/` 目录下新建** `YYYY-MM-DD-<slug>.md`。
3. **按上述格式填写**，重点写清“调试路径”和“经验教训”。
4. **在 `docs/NIT_ROADMAP.md` 或项目索引中**添加引用，方便检索。
5. **同步更新模板库**：如果该问题具有跨项目通用性，向 `Base-AI-Driven-Template/docs/playbooks/` 提交通用版本。

---

## 与 NIT_ROADMAP 的区别

| 文档 | 内容 | 时机 |
|------|------|------|
| `docs/NIT_ROADMAP.md` | 代码风格、重构建议、可优化点 | 每次 CR 后 |
| `docs/playbooks/<case>.md` | 具体 bug 的表象、根因、调试路径、修复、经验 | 解决棘手问题后 |
